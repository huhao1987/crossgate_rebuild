# 研究笔记：魔力宝贝资源、地图与协议

整理自对秋菟整合端（客户端资源）和 cgmsv 25.8 单机服务端的分析。本文只记录**格式和结构**，不包含游戏内容本身。
"已验证"表示在真实文件上抽样核对过；"推测"表示还需要用运行中的游戏确认。

---

## 1. 客户端图像资源

### GraphicInfo（每条 40 字节，小端）— 已验证
| 偏移 | 类型 | 含义 |
|---|---|---|
| 0 | int32 | 图像编号 |
| 4 | uint32 | 在 Graphic 文件中的偏移 |
| 8 | uint32 | 数据块长度 |
| 12 | int32 | 绘制偏移 X（相对锚点，地砖一般是 -32） |
| 16 | int32 | 绘制偏移 Y（地砖一般是 -24） |
| 20 | int32 | 宽 |
| 24 | int32 | 高 |
| 28 | uint8 | 占位格数（东向） |
| 29 | uint8 | 占位格数（南向） |
| 30 | uint8 | 通行标志：**1 = 可通行**（已用传送目的地验证，见第 5 节） |
| 31 | 5 字节 | 保留 |
| 36 | int32 | 地图编号（地图文件里引用的是这个，不是图像编号） |

### Graphic 数据块 — 已验证
`'RD'` + 版本(1) + 未知(1) + int32 宽 + int32 高 + int32 块长度，版本 ≥2 时再加 int32 调色板长度，然后是数据。
- 版本为奇数：数据经过 RLE 压缩；偶数：未压缩。
- 版本 ≥2：解压后像素后面跟着内嵌调色板（BGR 三元组）。
- 抽样解码成功率：主库 100%，Puk3 约 98.9%（失败的集中在版本 0/2 的边角情况）。

RLE 指令（高 4 位决定类型，低 4 位是长度最高位）：
| 指令 | 含义 |
|---|---|
| `0n` / `1n nn` / `2n nn nn` | 原样复制后面的 n 个字节 |
| `8n X` / `9n X nn` / `An X nn nn` | 把颜色 X 重复 n 次 |
| `Cn` / `Dn nn` / `En nn nn` | n 个透明像素（索引 0） |

### 调色板 .cgp — 已验证
224 色 × 3 字节（BGR），对应调色板索引 16–239。0–15 和 240–255 是固定的系统色（具体值**待用截图校准**）。索引 0 透明。

### AnimeInfo / Anime — 已验证
- AnimeInfo 每条 12 字节：uint32 动画编号 | uint32 偏移 | uint16 动作块数 | uint16 保留。
- 每个动作块的头：uint16 方向 | uint16 动作号 | uint32 时长(ms) | uint32 帧数，
  - BASE、EX 组：头 12 字节；
  - V3、Puk1–4、Joy 组：头 **20 字节**（多出 4 字节标志 + 4 字节 `FF FF FF FF`）。
- 每帧 10 字节：uint32 图像编号 + 6 字节标志（推测含音效/事件，未解析）。
- 主动画库每个动画 160 个动作块（推测为 20 种动作 × 8 方向）。

### 资源分组
服务端附带的 `cgmsv.yml` 的 BinLoader 段列出了每组 Graphic / GraphicInfo / Anime / AnimeInfo（V3 组还有 Coordinate、MapData、SeData）的对应关系，客户端按同样分组加载，后加载的覆盖先加载的。

## 2. 地图

### 客户端地图 `map/<楼层>/<编号>.dat`（小端）— 已验证
`'MAP'` + 版本(1) + 8 字节保留 + int32 宽 + int32 高，然后地面层、物件层、标志层各 宽×高 个 uint16，按行存储（index = y×宽 + x）。
- 抽查 300 张全部解析正确；地块值对应 GraphicInfo 的地图编号，约 97% 能在已加载的资源组里找到。

### 服务端地图 `服务端/data/map/<编号>_<地名>`（大端）— 已验证
`'LS2MAP'` + 2 字节 + 32 字节地图名（GBK，形如 `地名|数字`）+ uint16 宽 + uint16 高，然后地面层、物件层各 宽×高 个 uint16（**大端**）。
- 抽查 400 张：绝大多数正好两层；少数地图后面还有第三层和少量尾部数据（未解析）。
- 地块编号和客户端是同一套。服务端地图里没有单独的通行层，说明服务端也是用 GraphicInfo 判断通行（服务端自己也加载 bin 资源）。
- 共 5073 张，文件名里的编号就是地图 ID。

## 3. 协议线索（cgmsv）

- **封包是文本格式**：`包头 字段1 字段2 …`，空格分隔；数字用 **62 进制**；字符串需要经过 nrproto 转义（服务端 Lua 里有 `Protocol.nrprotoEscapeString / nrprotoUnescapeString`）。线上是否还有一层加密尚不清楚。
- **包头经过混淆**：`cgmsv.exe` 中 `nrproto_serv.c` 附近有一张 72 项的包头表，都是 2–4 个字母的标识，另有秋菟扩展的 `SWITM` 系列：

  ```
  Cpa QBt jmb aBS OaHi dAgg LYIm ELoy PudO vWpn xmgQ MTg Mhbt Ilz IYo lDuJ gnxd PhdQ
  aDn znv yuD Kka oRut Rll frQp HNP eZT IUn DpSY cNB DyAG KyN zdr aPc IsSy TNT nsY JJQj
  uSB cNE Rspn OBee SkBD sZWu bNY ysVc nFV JgO Cxo NdM nUbJ hJq RwK xEg BHe zzd TFCu
  wiB bJg PVfz murD ftaN TeD GmNM whV hPUd Daj HMNy cJzI LOh lSZ PfM
  扩展：SWITM SWITMP SWITMP2 SWITMM
  ```
  每个包头对应哪个操作，等封包日志拿到后对照。
- **服务端自带封包日志**：`cgmsv.cf` 第 3 行 `logPacket`，设为 1 后写入 `packet_<年月日时>.txt`（程序字符串显示包含 Send 方向）。**已在 `cg_single/_精简佣兵服务端/cgmsv.cf` 中打开**，原文件备份为 `cgmsv.cf.bak_before_logpacket`。
- **Lua 钩子**：`Protocol.OnRecv(…, 包头)` 能拦截客户端发来的包；程序里还有 `ProtoColSend` 回调的字符串，但 Lua 框架里没有找到注册接口。已加 `lua/Modules/protoLogger.lua`，把所有收到的包写入 `log/proto_recv.log`，作为封包日志的补充。
- 服务端源码文件名线索：`nrproto_serv.c`、`nrproto_util.c`、`mlsvproto_cli.c`、`char/char_send.c`。
- 客户端 `cg4.06cn.exe` 中有 `[Recv][%s]` 的调试字符串。

## 5. 用数据本身做的校准（不需要运行游戏）

- **通行标志**：传送表的目的地坐标一定是可走格。10971 个目的地中，能查到地面图像的 9449 个里 91.8% 地面标志为 1；目的地上的物件标志也几乎都是 1（2522 个，标志为 0 的仅 60 个）。结论：标志 1 = 可通行，地面和物件通用。
- **等距方向与物件占位**：对 2547 个多格物件做线性拟合，得到 `w ≈ 32×east + 32×south`、`ox ≈ -32×south`。说明东向往屏幕右上延伸，占位从锚点往东（+x）和往北（-y）展开，锚点是占位区最靠前的格子。用传送目的地交叉验证：按"东+北"占位，只有 0.70% 的目的地被误判为挡住，其它三个方向都在 8%–11%。
### 用 C# 数据层对全部真实数据的验证（CgPort.Tools validate）

- 5065 张服务端地图全部加载成功；GraphicInfo 共 58904 个地块编号。
- 传送表 10971 条：源点、目标地图、目标点 100% 在范围内。
- **可走物件铺地板**：地面不可走、但上面放着可走物件（桥、木板路等）的格子视为可走。加上这条规则后，传送落点可走率 78.6% → 82.4%，连通性不变；可走格总占比只从 15.9% 变为 16.1%。已采用（客户端 Demo 和服务端同一规则）。
- **连通性**：抽查 3000 个传送落点，99.8% 能沿可走格走到同图另一个出口——说明通行规则整体正确。
- 剩余约 18% 不可走的落点：约 860 个落在地面全为 0 的地图（推测是随机迷宫的空模板，地形运行时生成，见 dungeonconf.txt）；约 650 个的地面编号不在已加载的资源组里（推测在单机 7z 的 Puk5/Puk6 等组）；其余是地面标志为 0 且无可走物件的少数格子。
- 相邻地砖接缝颜色连贯性的方法区分度不够（四种方向差距很小），没有采用。

### 用真实数据模拟玩家（CgPort.Tools playtest / diag）

- 单机会话从法兰城（1000）出发，客户端按通行规则寻路、服务端逐步校验：4430 步中服务端拒绝 0 步；传送 108 次，到过 32 张地图。
- 法兰城本身没有遇敌区域；3 次传送内可达的 154 张地图中有 15 张有遇敌区域。在野外地图芙蕾雅（100）随机走 3648 步，遇敌 278 次。
- 遇敌率参数分布：10（2609 个区域）、1（967）、100（240）、5（216）、20（132）。
- 角色动画 100000：动作号 0–20（缺 4），每个动作 8 个方向。方向 0 各动作的帧数/时长：0=4帧/1000ms、1=6帧/1000ms、2=10帧、3=6帧/400ms、5=26帧/1500ms……推测 0 为站立、1 为行走（默认配置），待画面确认。
- NPC 外观编号约 30% 是动画、70% 是静态图像，客户端两种都要支持（已修）。

### 经验表与 NPC 脚本（已验证）

- **explist.txt**：第 N 行是升到 N 级所需的累计经验，严格递增，801 级。**enemyexplist.txt**：第 N 行是 N 级敌人给的经验，90 档。
- **npc.txt 第 24 列**是 NPC 脚本文件名（12640 个有脚本名的 NPC 中 7239 个能在 data/npc 找到）。
- **NPC 脚本语法**（统计 9634 个脚本得出）：`block 条件 && …` 为一条规则，从上往下执行第一条成立的；`window "文字",按钮…`（next/yes/no/ok）、`endwindow "文字"`；`window_yes/no/ok [条件]` 为按钮分支；分支内可有 `if/else/endif`；动作有 giveitem（含"(道具%权重,…)"随机给）、killitem、killitemall、addgold、warp 楼层,地图,x,y、endevent 编号 = 值、encount、message 等。关键字大小写不统一。
- **脚本引擎验证（CgPort.Tools scripts）**：9634 个脚本全部解析成功（42803 条规则、85876 个对话框）；动作支持 91.6%，条件支持 79.3%；新角色与 NPC 对话能弹出第一页的 77.4%，一路点下去 100% 正常结束。未支持的条件主要是聊天关键字、称号、声望、技能等级等，待相应系统实现。
